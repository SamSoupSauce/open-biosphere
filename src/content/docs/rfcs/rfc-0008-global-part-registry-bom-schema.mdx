## Status & Metadata
- **RFC ID:** RFC-0008 / DATA-001
- **Working Group:** Open-Hardware & Data Systems Working Group
- **Author:** Physical Systems & Supply Chain Architecture Team
- **Status:** Implemented
- **Supersedes / Refines:** Replaces hardcoded BOM markdown tables with canonical part IDs and structured registry linking
- **Target Subsystems:** Global Part Registry (`parts/`), Machine Stage BOMs, Sourcing & CAD Asset Pipeline
- **Release Target:** Open Biosphere v2.0-alpha

## 1. Executive Summary & Problem Statement

Prior to RFC-0008, components and raw stock materials were documented in isolated, hardcoded Markdown tables across individual machine documents. This caused significant operational and engineering friction:
1. **Redundant Metadata & Pricing Drift**: Shared components (such as NEMA steppers, MeanWell 24V power supplies, TB6600 drivers, ESP32 microcontrollers, and OLED displays) had duplicated, slightly differing price estimates and vendor references across different machines.
2. **Untracked Cross-Machine Synergies**: Builders could not easily generate a single consolidated shopping list when constructing multiple machines for a complete biosphere installation.
3. **Missing Fabrication Assets**: 3D-printable files (`.stl`, `.step`), CAD meshes (`.gltf`), and dimensioned vector engineering drawings (`.svg`) were not organized under a deterministic pathing schema.

**RFC-0008** establishes a centralized **Global Part Registry (`parts/`)** anchored by a canonical machine-readable database ([`src/data/parts.json`](/open-biosphere/parts/catalog/)), standardized part pages categorized by subsystem, public CAD/drawing asset storage, and bidirectional cross-machine dependency mapping.

## 2. Directory Hierarchy & Registry Structure

The Global Part Registry is structured across three core areas:

```text
src/
├── data/
│   └── parts.json                      # Machine-readable single source of truth
├── content/docs/parts/
│   ├── catalog.mdx                     # Interactive Global Part Registry & Search
│   ├── mechanical/                     # Extrusions, fasteners, bearings, shafts
│   │   └── <part_id>.mdx
│   ├── electrical/                     # Sensors, actuators, drivers, controllers
│   │   └── <part_id>.mdx
│   ├── fluidic/                        # Valves, pumps, nozzles, bulkheads, media
│   │   └── <part_id>.mdx
│   └── custom-fab/                     # 3D printed, laser cut, or welded assemblies
│       └── <part_id>.mdx
public/
└── assets/parts/
    └── <part_id>/
        ├── photo.webp                  # Physical component photo or 3D render
        ├── model.gltf                   # Canonical glTF 2.0 3D CAD model
        ├── model.gltf                   # Scalable 3D CAD mesh
        ├── print.stl                   # Slicer-ready 3D print file (if custom-fab)
        └── cad.step                    # Parametric CAD solid model (if custom-fab)
```

## 4. Machine Stage BOM Linking Specification

In each machine's `stage-X.mdx` document, BOM tables are updated to bind directly to the registry:
1. **Canonical ID**: Links to the part specification page (`PART-MECH-WEDGE-150U`).
2. **Part Name & Description**: Links to `/open-biosphere/parts/<category>/<part_id>/`.
3. **Supplier & SKU**: Links to primary COTS supplier.
4. **Fabrication Type**: Stock COTS, 3D Print, or Custom Fabrication.
5. **Quantity & Pricing**: Unit cost, stage quantity, and extended line cost.
6. **CAD Asset Link**: One-click download button for 3D model / dimensional drawing.

---

## 5. Security, Sourcing Integrity & Verification

- **Multi-Vendor Redundancy**: Every COTS component specifies at least one domestic/rapid supplier (e.g. McMaster-Carr, Amazon, DigiKey, Adafruit) and one direct-manufacturer source (e.g. AliExpress, StepperOnline, LCSC) to protect against localized supply chain bottlenecks.
- **Air-Gapped Local Assets**: All CAD models, vector drawings, and print files are stored locally in the repository under `public/assets/parts/`—zero external CDN dependencies.
